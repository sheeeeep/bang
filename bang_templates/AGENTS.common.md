# 仓库指南

## 协作与授权

- 使用中文沟通和编写注释；命令、标识符和原文引用保留原样。
- 围绕用户指定的任务持续推进实现、验证和修复，直到满足完成条件；多个任务逐项执行。仅在用户要求自主选择下一项工作时，按 `feature_list.json` 的优先级选择。
- 已授权范围内的只读检查、本地编辑和非破坏性验证自行执行，无需逐步确认。普通、可逆的技术选择沿用现有模式，影响结果的假设在交付时说明。
- 先查现有资料；只有缺失信息会实质影响目标行为、范围、兼容性、安全性或不可逆结果时才集中询问。用户明确要求的“先提方案”“修改前确认”“暂不提交”和工具要求的批准仍须遵守。
- 推送、发布、部署、破坏性操作和全局环境变更须有明确授权；已有授权不重复询问。登录及权限授予由用户完成，受阻时继续可独立推进的工作。

## 编码约定

- 禁止静默吞掉错误；错误须有用户可感知的反馈并记录日志。
- 本次新增或修改的命名函数须有简短中文 JSDoc；其余注释只解释复杂或不明显的逻辑，不补齐未修改代码的注释。
- 新增文件（测试和样式文件除外）用 3～6 行中文文件头说明业务角色、具体问题、触发条件与输入、关键动作与结果。容易混淆时说明相邻模块的职责；涉及异步状态时说明实际存在的超时、并发合并和清理规则，不为注释新增机制。用具体动作描述业务链路，不只复述目录或 Service 名称。

## 验证与阻塞

- 按任务验收标准及相关包要求执行验证；未指定时，选择覆盖改动行为的最小有效检查。需要区分已有失败或复现问题时先跑基线。文档或配置修改只做相关检查，不机械运行全量测试或启动浏览器。
- 检查失败时区分本次缺陷、已有无关失败和环境问题；仅修复授权范围内的问题，重跑受影响的检查。无新证据时不重复同一失败方法；检查工具、Node 版本、EMO 用法、依赖、权限或相关文档后调整方法。
- 完成意味着目标行为已实现、必需验证实际通过、验证证据已记录，且仓库可按标准启动路径恢复工作。不得降低验证标准或把未验证写成通过；受阻时说明已做事项、未验证内容、具体原因和恢复步骤。

## 任务记录与交付

- 已纳入 specs 的实现任务，读取并维护 `specs/<任务名>/`：`spec.md` 描述功能，`feature_list.json` 是功能状态的唯一事实来源，`progress.md` 记录进度、验证命令与结果、风险和恢复步骤；长会话可补充 `session-handoff.md`。
- 需要长期跟踪的新功能建立上述目录，用户指定路径优先。持久化记录用于恢复上下文，不覆盖用户本轮指示；存在无法判断且影响范围或正确性的冲突时询问。
- 只读审查、解释和方案讨论不创建或更新任务文件；无现有任务目录的小型独立修改，在交付中记录改动范围、验证结果和剩余风险即可。
- 已授权的实现改动在必需验证通过且无未解决阻塞后，按仓库提交流程创建本地提交，无需重复确认；用户要求暂不提交时不提交。纯审查不提交。
- 只提交本任务修改，不擅自 amend、重写历史或推送。无法安全区分改动归属时保留工作区并报告；目标文件被 Git 忽略时不强制加入版本管理，交付时说明。
