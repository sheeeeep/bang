# 个人规格生成

此技能基于当前对话上下文和对代码库的理解，生成一份规格说明。不要向用户进行访谈式提问；只需综合整理已有信息。

你应该已经获得了议题跟踪系统的信息和分流标签词表。如果没有，请提示用户运行 `/setup-matt-pocock-skills`。

## 流程

1. 如果尚未了解代码库的当前状态，先探索仓库。在整份规格说明中使用项目领域术语表中的词汇，并遵循涉及领域的所有架构决策记录（ADR）。

2. 概述计划在哪些测试接入点（seams）测试该功能。优先使用现有接入点，而不是新增接入点。尽可能选择最高层级的接入点。如果需要新增，也应在尽可能高的层级提出。代码库中的测试接入点越少越好，理想数量是一个。

   与用户确认这些测试接入点是否符合其预期。

3. 使用下方模板编写规格说明，然后将其发布到项目的议题跟踪系统。添加 `ready-for-agent` 分流标签，无需进一步分流。

<spec-template>

## 问题陈述

从用户的角度描述用户面临的问题。

## 解决方案

从用户的角度描述问题的解决方案。

## 用户故事

一份详尽的、带编号的用户故事列表。每条用户故事应采用以下格式：

1. 作为<角色>，我希望<功能>，以便<收益>。

<user-story-example>
1. 作为手机银行客户，我希望查看各账户的余额，以便对支出做出更明智的决策。
</user-story-example>

这份用户故事列表应尽可能详尽，覆盖该功能的所有方面。

## 实现决策

列出已经做出的实现决策，可包括：

- 将要构建或修改的模块：使用真实业务词汇和 Module 名称；新增 Module 明确标记。
- 这些模块中将要修改的接口
- 开发者提供的技术澄清
- 架构决策：
  - 优先复用既有模式；用第二调用方检查重复风险，但不为假想需求增加抽象。
  - 保留邻近行为，不夹带重构或已知问题修复；同一概念命名一致。
- 数据模式（Schema）变更
- API 契约
- 具体交互
- 仅在图能减少解释成本时使用 Mermaid，默认最多一张；按需标记【新增】【改动】【复用】，不强制绘制时序图。

不要包含具体文件路径或代码片段，它们可能很快就会过时。

例外：如果原型中产生的代码片段比文字更能准确表达某项决策（例如状态机、归约器、数据模式或类型结构），请将其直接放在相关决策中，并简要注明它来自原型。只保留体现决策的关键部分，不要放入完整的可运行演示。

## 测试决策

列出已经做出的测试决策，包括：

- 什么样的测试才是好测试（只测试外部行为，不测试实现细节）
- 将要测试哪些模块
- 可参考的现有测试实践（即代码库中类似类型的测试）

## 范围之外

说明哪些事项不在本规格说明的范围内。

## 补充说明

关于该功能的其他补充说明。
